# Decision register and open questions

## Locked decisions

- Expo/React Native + FastAPI + Postgres/SQLAlchemy/Alembic; Railway target.
- ThinkSo is a public GitHub monorepo organized by feature. Mobile features own their UI/presenter/data mappings; backend features own HTTP/job adapters plus application/domain/persistence code. HTTP, worker, and scheduler remain separate thin entrypoints. Normal tickets and pull requests deliver one small observable full-stack feature; explicitly labeled enabling infrastructure work is the exception.
- Tooling is pnpm for TypeScript, uv inside the container-first Python backend, Docker Compose locally, a root `justfile`, and GitHub Actions. Mobile gates use Expo ESLint, Prettier, `tsc`, Jest, and React Native Testing Library; backend gates use Ruff, mypy, and pytest.
- Deep pull-request delivery uses GitHub's native stacked-PR public preview through GitHub CLI 2.90.0 or later and the official `github/gh-stack` extension. The coordinator owns all stack mutations; hand-written PR retargeting, cascading rebase automation, and alternate stack tools are excluded unless the native preview proves insufficient.
- ThinkSo is public and source-available but is not currently open source. Copyright is reserved by Mitchell Jackson; no general software license is granted, and outside contributions are not accepted initially to preserve clear ownership and future relicensing options. A possible later GPL release is explicitly deferred and does not grant present rights.
- Ordinary CI is emulator-free on standard Linux runners. AutoMobile drives local Android and iOS native review. Hosted E2E is deferred and begins with Android; paid hosted iOS is not assumed.
- Apple and Google login are implemented and fake-tested together behind the shared provider boundary. The free iOS Simulator exercises feasible flows through Google; only live Apple credentials/entitlements and end-to-end Apple verification wait for paid enrollment. Expo Push Service remains the cross-platform notification relay. Push implementation follows acceptance, judging, and consequence publication rather than blocking those core features. Android receives live delivery coverage; live APNs delivery, TestFlight, and App Store verification wait for paid Apple Developer enrollment.
- Railway account creation, billing, deployment secrets, stable production domains, and production URLs are deferred until deployment is chosen. Local Docker Compose and temporary development tunnels must support implementation without those purchases.
- The backend is a feature-oriented FastAPI modular monolith. Dishka owns application, request, and worker-job dependency scopes. I/O is async through FastAPI, SQLAlchemy `AsyncSession`, psycopg 3, provider clients, and workers; pure domain code remains synchronous. One application operation owns one transaction, repositories never commit, and transactions never remain open across slow provider calls. PgQueuer provides Postgres-backed durable jobs behind a `TaskQueue` port; Redis and Celery are excluded until a concrete requirement justifies them.
- PydanticAI is the minting/judging harness and OpenRouter is the initial model gateway. Both agents initially use the fixed `z-ai/glm-5.3-flash` model ID, configured independently and versioned with every attempt. OpenRouter may route and fail over across providers serving that fixed model, but may not automatically substitute a different model ID. OpenRouter web search is the initial research adapter behind a typed `WebResearch` port. PydanticAI owns model/tool loops and streaming only; ThinkSo owns durable execution, persistence, cancellation, authorization, SSE, validation, and state transitions.
- New user-initiated minting-agent turns are gated by a USD $0.25 per-user UTC-calendar-day spend budget. Each run receives the user's remaining budget; actual model and research charges are added after every provider response, and no further step starts once exhausted. Only the already-in-flight request may produce a bounded overage; search uses/results and model output are capped per request. System-required judging, publication, notification, and completion retries are never blocked by this budget. Verified owner emails are unlimited through deployment-secret configuration and are not hardcoded in the public repository. The demo uses a dedicated production OpenRouter key with matching application-side and provider-side USD $25 daily limits, prepaid credits, manual refill, and no automatic top-up as the final global blast-radius control; this is adjustable operations configuration rather than permanent product pricing.
- Budget exhaustion rejects the attempted message before persistence, retains its draft while Create Challenge remains mounted, adds an authoritative non-agent conversation notice, and shows a non-retryable DAILY LIMIT toast. Submission stays disabled until the server-supplied reset time, while reading/selecting proposals and sending an existing proposal remain available. Leaving follows the ordinary discard warning and creates no special recovery path.
- If the daily budget is reached during a minting turn, finish accounting for the current provider response, start no further model/search step, end the turn as BUDGET_EXHAUSTED, preserve visible partial text as incomplete, and emit the same authoritative notice. After reset, retry reuses the persisted triggering message without duplication.
- The mobile client uses a Presenter/UDF architecture modeled on Slack Circuit. Generated DTOs remain inside transport/data; repositories map DTOs to domain models; data-layer TanStack Query definitions own server caching, subscriptions, keys, policy, mutations, and invalidation. Obsidian injects application/feature graphs, repositories, data definitions, typed effect ports, and custom-hook presenters. Presenters hold transient state with React, may compose other presenters, return discriminated presentation-ready `UiState` containing one typed `onEvent` callback, and own navigation/effect decisions. React Native components only render state and emit events. Presenter implementations are unit-tested with `renderHook` and injected fakes. RxJS, Redux, Zustand, field injection, Obsidian observables, and service location are excluded unless a new concrete requirement changes the architecture.
- Unit and layer-level tests are written with the production code they protect. Full E2E automation is deferred until the complete product flow exists and then lives in a separate suite, intentionally overlapping critical unit-tested behavior.
- Vertical slices, not layer-first phases.
- Tablets reuse the phone UI in a centered maximum-width content column; MVP has no special tablet design. Portrait is required. Rotation may remain enabled when the normal responsive layout is usable, but may be locked to portrait rather than adding landscape-specific design or delaying delivery.
- Primary login uses one endpoint with Apple/Google provider field.
- One active profile may link both Apple and Google identities. Provider subjects are namespaced by provider. Apple subjects, Google subjects, provider-verified normalized emails, and the Threads user ID are independent identity signals. Permanent retirement tombstones all observed signals; a match on any one rejects future login, profile creation, or Threads connection as the same retired user. This layered model is intentionally proportionate to a low-stakes recreational product and is not legal identity verification.
- Threads is a linked required social identity, not a primary login method.
- Main is the internal screen name; THE RECORD is its UI title.
- Main has OPEN/CLOSED only; the server defines membership and ordering. List entries carry an explicit server-issued `record_order`; clients do not infer ordering from response-array position. OPEN priority is: awaiting acceptance newest-sent first, judging/retrying earliest-due first, then accepted/upcoming earliest-judgment first, with a stable unique server tie-breaker.
- For MVP, OPEN ordering buckets are not rendered with group headings; the cards form one continuous list and retain their individual status labels. Revisit after observing the design in use.
- CLOSED is server-sorted by terminal-state timestamp descending across resolved, expired, voided, and terminal-unresolved records; creation time does not determine its order.
- Every fresh entry to Main defaults to the OPEN tab. The app does not remember the previously selected tab across entries.
- The CLOSED tab is shown only when the user has at least one challenge in the server-defined CLOSED set. It is hidden when that set is empty.
- An empty OPEN set never causes automatic selection of CLOSED. Fresh entry still shows the OPEN empty state, with CLOSED available only when closed records exist.
- OPEN uses one empty-state variant regardless of CLOSED history: `NOTHING OPEN` / `No challenges need your attention. Go start something.`, with the existing crossed-out-document art and direction toward Make a Challenge.
- The Make a Challenge FAB remains available across all Main tab/data states, including loading and recoverable list errors. Session and Threads gates remain authoritative exceptions.
- One MVP Record request returns both complete OPEN and CLOSED collections. Tab selection is local and never causes a separate fetch.
- MVP Record pagination is deferred. The full returned collection uses explicit `record_order`; add pagination later only when observed size/performance requires it.
- Main pull-to-refresh reloads both Record collections atomically. Refresh preserves retained cards and uses a small loading S; failure preserves the retained Record and shows the global retry toast. Full-screen error is used only when no usable Record exists.
- For MVP, when Main regains focus, it immediately shows the retained Record and silently refreshes both collections through the repository. Focus-refresh failure preserves usable cards and shows the retry toast; full-screen loading remains limited to absence of usable Record data. Revisit after observing real usage.
- Initial Record load failure uses `THE RECORD WON’T OPEN`, the exported explanatory copy, `TRY AGAIN`, `hit it again`, and the persistent FAB. Retry disables its button and shows the separate loading S without discarding the error composition; success shows the Record and repeat failure restores retry.
- One canonical full `Contract` serialization everywhere.
- Direct Contract, Record, and user reads are platform-public for MVP: they require an active ThinkSo session and connected Threads account, but are not owner- or participant-restricted. Anonymous internet previews are deferred.
- Chat uses a long-lived GET SSE stream; POST only submits a message/starts a turn.
- Initial `chat_state` is full and authoritative; no MVP chat pagination.
- Clients ignore unknown SSE events.
- Client-generated message UUID is unique within the chat; duplicate is a conflict/recovery signal.
- One active agent turn per chat; disconnect does not cancel it.
- During SSE disconnection, transcript/proposal reading and selection plus composer editing remain available, but the composer action becomes a non-submitting `RECONNECTING...` loading-S treatment. Authoritative chat state restores Stop or Submit after reconnect without clearing draft text.
- When automatic SSE reconnection attempts are exhausted, the composer action becomes tappable `RETRY CONNECTION`. Retrying does not clear the draft or restrict reading and selecting proposal cards.
- Active minting-agent output and sending an existing proposal may proceed concurrently. An active turn does not disable proposal selection or `CREATE + SEND`.
- A successful proposal send ends the creation flow. Any concurrently active minting turn is canceled, and late output cannot surface or alter the sent immutable contract.
- Create Challenge follows streaming content only while the user is near the bottom. Scrolling upward transfers control of the position to the user and disables automatic following until they return to the bottom.
- MVP has no new-content or jump-to-latest control while Create Challenge is scrolled away from the bottom; reconsider after MVP.
- The Create Challenge composer expands through five visible lines and then scrolls internally.
- Return inserts a newline in the Create Challenge composer. Message submission occurs only through the composer arrow.
- Retrying a failed minting-agent turn reruns only the agent turn associated with the already-persisted user message. It never resends or duplicates that message.
- While the minting agent is turning, the composer submit control becomes a red Stop control. No second message is queued or submitted; Stop cancels the active turn and then restores normal sending for the same chat.
- A stopped turn retains its streamed text as a user-visible STOPPED assistant message. Later model context is rebuilt from persisted ThinkSo messages and includes that partial text plus an interruption marker, while incomplete provider tool-call items remain private and are not replayed as dangling protocol context.
- The minting composer remains editable during an active turn. Stop does not clear its draft; only successful submission of that exact draft clears the field.
- Failed message submission restores the exact text to the composer, removes or reconciles the optimistic message, and uses the global retry toast without creating a duplicate server message.
- Every proposal is persisted and immutable before SSE emission; revisions create new rows.
- Every minting proposal must predeclare and verify its future judgment sources or source hierarchy. Use web research whenever verified context is insufficient, which is expected for most real proposals; do not require redundant searches solely as ceremony.
- The minting agent is purpose-bound to challenge creation. Questions and research reasonably directed toward forming, verifying, timing, or revising a Contract are allowed. Unrelated general-assistant work, including standalone schoolwork, is declined briefly and redirected to challenge creation without spending research/tool calls on the unrelated task.
- Judgment sources are not a separate structured Contract field. They are part of the immutable official resolution terms, which the judging agent receives prominently and follows as its source contract.
- The immutable resolution terms and their stated source hierarchy control judging. If every permitted source is unavailable, the judge retries within the existing window and ultimately returns UNRESOLVED at Resolve By; it may not silently substitute an unmentioned source.
- Evidence sufficiency is contract-specific, not a global citation count. One authoritative source may resolve an official score or number. Claims established by reporting or consensus must state an explicit agreement rule in the official terms, such as concurrence among three qualifying major trackers. The judge must satisfy that rule before returning a verdict.
- A supported TRUE or FALSE verdict is final for MVP. Participants cannot appeal, request rejudging, or override it. Appeals and formal correction workflows are deferred to V2.
- Judging receives at most eight substantive evidence attempts distributed across First Judgment through Resolve By, including an immediate first attempt and a final attempt at Resolve By. Infrastructure recovery may retry the same attempt without consuming another evidence slot, and a supported verdict cancels the remaining schedule.
- MVP consequences are posts only. Each possible losing participant has exact pre-approved Threads post text selected deterministically by the verdict. Minting must reject or rewrite profile changes, offline dares, payments, physical acts, and other manual consequences that ThinkSo cannot execute.
- A prospective newsworthy event need not already have its final-result page. Minting must establish a credible future evidence path and source hierarchy. If no objectively judgeable path exists, the agent refuses to propose and asks the user to change or clarify the challenge.
- The proposal tool requires explicit Accept By, First Judgment, and Resolve By values and has no programmatic date fallback. Hard validation requires Accept By before First Judgment and a judging window of at least 48 hours. Seven days is prompt guidance for the normal judging window, not a validator or acceptance-window rule.
- The acceptance deadline is an exact timezone-qualified instant stored as UTC. User-facing proposal, card, and sent-Contract UI shows a snapshot-relative `ACCEPT IN ...` label computed on authoritative load/refresh, not a running countdown. Floor the largest complete unit: 2.5 days → 2 days, 1.2 hours → 1 hour, five minutes → 5 minutes, and any positive duration below one minute → `NOW`. Server expiration and atomic acceptance remain authoritative.
- First Judgment and Resolve By render as exact device-local calendar date, clock time, and timezone, not date-only or relative values. Include seconds when a stored instant is not minute-aligned. These fields do not run as countdowns; the stored UTC instants remain authoritative.
- Create Challenge is text-only for MVP. Hide the exported attachment control and do not create an upload API without a defined use case and policy.
- Every Make a Challenge action starts a new minting chat. Unfinished chats are not resumed as the current creation flow. Attempting to leave after the flow begins requires an explicit DISCARD or CONTINUE decision.
- New minting chats persist `Okay, let's hear it. What are you so sure about?` as the first assistant message; it is returned in chat state and included in model context rather than rendered as static-only copy.
- Initial chat creation shows the Create Challenge shell with the centered loading S and disabled composer. The greeting and enabled composer appear only after persistence succeeds.
- Initial chat-creation failure retains the shell and Back, disables the composer, and uses the global retry toast. Retry must not create duplicate chats or greeting messages.
- The discard guard fires when at least one message was submitted or the composer contains unsent text. Exit is immediate only when no messages were submitted and the composer is empty.
- The exit dialog uses `THROW THIS OUT?`, `KEEP WORKING`, red `DISCARD`, and the annotation `commitment issues already?`; it says the draft and conversation cannot be recovered.
- DISCARD marks the chat ABANDONED and makes it permanently inaccessible to the user. Its chat, messages, turns, and unsent proposals remain private internal records for eval/training/history; actual training use requires disclosure and retention/access policy before release.
- Discarding an active minting chat explicitly cancels its active turn where possible. Late provider output may be retained privately but cannot reactivate the chat or create user-visible messages/proposals.
- `send`: PROPOSED → SENT; `accept`: SENT → ACCEPTED. The MVP has no decline transition or endpoint.
- The invite's `REJECT` control closes the Contract locally without a request, state change, or notification. True targeted rejection and DECLINED state are deferred to V2. Already accepted always conflicts.
- First valid acceptance is atomic and wins.
- Every Contract stores immutable `creator_display_name` and `opponent_display_name` text. The creator label defaults from the account display name captured from primary login and may be changed by the minting agent for one proposal without changing the profile. The Contract displays the creator's Threads handle and, after acceptance, the bound challenger's Threads handle. No challenger handle exists before acceptance; the intended-opponent text remains visible after binding.
- `opponent_display_name` is immutable descriptive text, not access control. If a different link-holder accepts first, retain that intended-opponent text and separately display the authenticated bound challenger.
- MVP forbids creator self-acceptance in both UI and API authorization. Solo/self challenges are a valid V2 use case, not part of the initial state machine.
- Creator uses native share sheet; no custom success/share screen.
- Creator confirmation describes platform-public access accurately: `Anyone on ThinkSo with the link can view it. The first person to accept is locked in.`
- Creator send disables both confirmation actions and shows the loading S. Failure closes the dialog, preserves the PROPOSED contract, and offers global-toast retry without requiring a second confirmation.
- Recipient remains on the same Contract screen after acceptance; no success screen.
- Judgments live on the Contract screen; no judgment destination.
- A supported verdict transitions `JUDGING → POSTING`, not directly to RESOLVED. POSTING exposes the final verdict and a generic POST PENDING treatment while durable publication work runs. Successful Threads publication and persisted receipt transition `POSTING → RESOLVED`; publication retry never reruns the judge.
- Invalid/revoked Threads authorization pauses publication without blind retries, pauses the 24-hour active-delivery clock, and gates the user to Connect Threads. Successful reauthorization resumes blocked publication jobs. Temporary publication failures receive eight attempts over 24 active delivery hours.
- After an ambiguous Threads timeout, publication reconciles the losing participant's recent posts for the exact approved text before any repost. A found post supplies the recovered receipt; confirmed absence permits retry; unresolved ambiguity never triggers a blind duplicate. Permanent nonauthorization rejection or failure to establish safe completion by the end of the delivery window transitions the Contract from POSTING to VOIDED and cancels further delivery.
- POSTING remains nonterminal. If either participant permanently retires before publication succeeds, the Contract becomes VOIDED, pending publication is cancelled, and any unpublished verdict remains private operational history.
- A user has many push tokens. MVP transactional events are acceptance, supported verdict ready (`POSTING`), and `UNRESOLVED`.
- Acceptance sends a push to the creator. A supported verdict entering POSTING sends one result push to both participants; RESOLVED does not send a duplicate. UNRESOLVED also notifies both participants. Every push opens the canonical Contract.
- The POSTING result push intentionally withholds TRUE/FALSE on the lock screen. Its user-facing message is exactly `Your judgment is in!`; the user opens the Contract to see the verdict and evidence.
- The acceptance push says exactly `Your challenge was accepted!` and opens the accepted Contract.
- The UNRESOLVED push says exactly `We couldn't resolve your challenge.`; both participants receive it and it opens the Contract.
- A SENT Contract becoming EXPIRED does not send a push notification. It moves silently into the creator's CLOSED Record.
- A Contract becoming VOIDED does not notify either participant in MVP. The remaining active participant discovers the terminal state in CLOSED or on the next Contract refresh; a dedicated void notification is deferred.
- Request notification permission contextually after the user's first successful Contract send or acceptance on that device, whichever occurs first. Show a ThinkSo primer before invoking the native operating-system prompt; never display the native prompt before the triggering mutation succeeds.
- The notification primer is a compact paper-notice dialog: `THINKSO · NOTICE`, `OPTIONAL`, `GET THE RECEIPTS`, body `ThinkSo will let you know when a challenge is accepted and when a judgment is ready. That's it.`, actions `TURN ON NOTIFICATIONS` and `NOT NOW`, and handwritten `you'll want this`. Show it at most once per installation and skip it when permission is already granted or permanently denied.
- Disconnect is always allowed and permanently retires the profile, voids unresolved challenges, invalidates sessions/removes push tokens, and preserves public history.
- Ordinary Sign Out is current-device-only and local-first. Local credentials and protected state are cleared immediately; server-session revocation is best-effort and cannot block logout. Other device sessions remain active.
- Permanent retirement requires the complete five-second hold shown in the final warning. Early release resets progress. After completion, both dialog actions remain disabled with the loading S until the server transaction succeeds or fails; failure preserves the session and offers normal error recovery.
- A retirement failure's global TRY AGAIN repeats the already-confirmed request without another hold while the final flow remains open. Leaving the flow clears that confirmation; a later attempt requires both warnings and a new five-second hold.
- Minting may allow profanity, ordinary name-calling, harsh self-deprecation, edgy jokes, rivalry trash talk, and consensual embarrassment within reason. Mere offensiveness is not the refusal boundary. It must refuse protected-class attacks, targeted harassment, credible threats, private information, impersonation/deception, illegal acts, or genuinely dangerous conduct. Context, consent, target, repetition, and severity matter. This boundary requires adversarial validation and regression evals before release.
- Build useful creation agent first, judge second, evals from real failures third, APO later.
- ThinkSo sessions use opaque database-backed access tokens with a 24-hour lifetime, rotating refresh credentials with a 30-day idle and 180-day absolute lifetime, and a 30-second previous-token recovery grace window. Clients refresh within the final hour or once after `401`; server-side revocation remains immediate.
- Threads authorization state is `NEVER_CONNECTED`, `CONNECTED`, or `REAUTH_REQUIRED`. Never-connected and externally revoked profiles are gated to Connect Threads and cannot enter Main, view in-app history, mint, accept, or perform authenticated product actions until authorization succeeds. External revocation does not retire the profile; only in-app Disconnect does. Connected profiles are verified at least every six hours, with live verification permitted before consequential actions.
- A Threads identity already linked to another active profile causes a hard connection failure. MVP never permits duplicate ownership, transfers the connection, or merges profiles automatically. Connect Threads shows an already-claimed toast with `LOG OUT · 6` instead of retry; logging out changes neither profile. Account transfer and recovery are post-MVP.
- If Threads OAuth succeeds on the backend but the mobile return/deep link is missed, Connect Threads focus or the next bootstrap observes server-owned `CONNECTED` state and routes directly to Main without a toast or repeat authorization.

## Explicit non-questions for MVP

Do not reopen these without new product direction: feeds/discovery, separate judgment screen, contract summary serializer, WebSockets, editing/withdrawing a sent challenge, a bespoke share screen, configurable notification categories, profile/avatar editing, exact minting-agent failure/refusal prose where the BDD-defined behavior is preserved, or APO before a working product and real eval corpus.

## Later demo hardening

- Accessibility and screen-reader acceptance criteria are not part of the initial demo slice. Revisit them before treating the app as production-ready.
- MVP improvement: cap cumulative judging inference and research spend at USD $1.00 per Contract. Reaching it pauses automatic attempts and creates operator-visible review work rather than falsely transitioning to UNRESOLVED.
