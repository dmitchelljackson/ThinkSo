# API specification

## Status and conventions

This is the current MVP contract. Endpoint purposes and lifecycle behavior are **LOCKED**. Names/types marked **DERIVED** make the agreed behavior implementable where the source did not preserve a final literal schema. Keep the OpenAPI document generated by FastAPI synchronized with this file.

- Base path: `/v1` (**DERIVED**; omit or change consistently before clients ship).
- JSON keys: `snake_case`.
- IDs: opaque UUID strings unless otherwise stated.
- Times: UTC ISO-8601 strings.
- Authentication: `Authorization: Bearer <access_token>`.
- Empty mutation bodies: no request body, not `{}`.
- Canonical mutation result: return the full canonical `Contract`.
- Unknown JSON response fields must be ignored by clients.

### Foundation health

`GET /v1/health` is public and returns the API process health snapshot:

```json
{
  "status": "ok",
  "service": "thinkso-api",
  "version": "0.0.0",
  "checked_at": "2026-09-04T14:30:57.255022Z"
}
```

`checked_at` is a UTC instant. The endpoint is a process/readiness signal for local and deployment smoke checks; it does not replace feature authorization or database migration checks.

### Error response

```json
{
  "error": {
    "code": "contract_state_conflict",
    "message": "This challenge has already been accepted.",
    "details": {}
  }
}
```

Use stable machine-readable `code`; `message` is safe to display; `details` is an object and may be empty. Recommended statuses: 400 validation, 401 unauthenticated, 403 ineligible/retired, 404 absent, 409 duplicate/state conflict/active turn, 410 expired public artifact when applicable, 422 schema validation, 429 daily spend gate, 500 internal failure.

## Canonical schemas

### UserRef

```json
{
  "id": "uuid",
  "display_name": "Mitchell",
  "is_retired": false,
  "social_identity": {
    "provider": "threads",
    "username": "mitchell",
    "profile_url": "https://www.threads.net/@mitchell"
  }
}
```

`social_identity` may be `null` only where no linked identity can be retained. In a Contract, the creator's Threads identity is present, and the challenger's Threads identity is present after acceptance. Their public handles remain part of preserved Contract history after retirement. Avatar URLs, provider-native IDs, counts, and additional profile fields are omitted from the MVP public contract.

### Consequence

Each Contract contains exactly two MVP consequences, one for each possible losing side. Before acceptance, the eventual challenger's `participant_id` is null; acceptance binds it without changing the approved text.

```json
[
  {
    "id": "uuid-creator-loses",
    "participant_id": "creator-uuid",
    "triggering_result": "FALSE",
    "post_text": "I was wrong about the Bears.",
    "destinations": [
      { "provider": "threads", "status": "PENDING", "external_post_url": null }
    ]
  },
  {
    "id": "uuid-challenger-loses",
    "participant_id": null,
    "triggering_result": "TRUE",
    "post_text": "The Bears proved me wrong.",
    "destinations": [
      { "provider": "threads", "status": "PENDING", "external_post_url": null }
    ]
  }
]
```

`participant_id` may be null in a `PROPOSED`/`SENT` contract if the consequence targets the eventual challenger (**DERIVED**). After a verdict, the selected loser's destination remains `PENDING` until publication and the unselected destination becomes `NOT_REQUIRED`. Public destination status: `PENDING | POSTED | NOT_REQUIRED`. Retry, reconciliation, and blocked-authorization states are private publication-job details.

For MVP, `post_text` is the complete consequence. Each possible losing side has exact pre-approved Threads post text, and the verdict deterministically selects the losing participant's post. Do not represent profile changes, offline dares, payments, physical acts, or other manual consequences in the proposal tool or public API.

### Verdict

```json
{
  "result": "TRUE",
  "evidence_markdown": "The official result was ... [source](https://example.com).",
  "judged_at": "2027-01-06T03:00:00Z"
}
```

Result is `TRUE | FALSE`. Internal judge attempts are never included in the normal client response.

### Contract

```json
{
  "id": "uuid",
  "public_id": "TS-000421",
  "state": "ACCEPTED",
  "title": "BEARS WIN 10 GAMES",
  "creator_display_name": "Mitchell",
  "creator": { "id": "creator-uuid", "display_name": "Mitchell", "is_retired": false, "social_identity": { "provider": "threads", "username": "mitchell", "profile_url": "https://www.threads.net/@mitchell" } },
  "challenger": { "id": "challenger-uuid", "display_name": "Donald", "is_retired": false, "social_identity": { "provider": "threads", "username": "dontpuntedme", "profile_url": "https://www.threads.net/@dontpuntedme" } },
  "opponent_display_name": "Don",
  "resolution_contract": "TRUE if ...; otherwise FALSE. Source hierarchy: ...",
  "resolution_date": "2027-01-05T00:00:00Z",
  "resolution_expiration": "2027-01-12T00:00:00Z",
  "acceptance_expiration": "2026-09-07T00:00:00Z",
  "created_at": "2026-08-31T18:00:00Z",
  "sent_at": "2026-09-01T18:00:00Z",
  "accepted_at": "2026-09-02T18:00:00Z",
  "terminal_at": null,
  "resolved_at": null,
  "consequences": [],
  "verdict": null
}
```

State: `PROPOSED | SENT | ACCEPTED | JUDGING | POSTING | RESOLVED | EXPIRED | VOIDED | UNRESOLVED`.

In `POSTING`, `verdict` is present and final but the required Threads consequence receipt is not yet available. `verdict.judged_at` records when judgment committed. `RESOLVED` requires successful publication and a persisted provider post identifier/link; `Contract.resolved_at` records that later transition. `terminal_at` is set for every terminal state and drives CLOSED ordering. Provider retry details remain internal and are not serialized in the canonical Contract.

One serialization is used in direct reads, list-entry envelopes, chat proposals, and mutation responses. A list entry nests the unchanged canonical contract beside list-specific ordering metadata; it does not create a summary/detail contract variant. Nullable fields remain present as `null`. MVP omits viewer-relative action flags: clients derive visible controls from authenticated identity, state, and timestamps, while every mutation repeats authoritative server eligibility checks.

`creator_display_name` and `opponent_display_name` are immutable descriptive Contract text, not access-control identities. Because a connected Threads account is required before minting, the creator label defaults from the creator's Threads profile name or handle; the minting agent may change that label for one proposal without changing the user profile. The authenticated user who wins acceptance is stored separately in `challenger`. If the intended name and actual challenger differ, clients display both: the original intended-opponent wording remains unchanged and the bound challenger identity is identified separately. The creator's Threads handle is always displayed with the creator label; after acceptance the bound challenger's Threads handle is displayed with the opponent label. Before acceptance there is no challenger handle to show.

The minting proposal tool requires explicit `creator_display_name`, `opponent_display_name`, `acceptance_expiration`, `resolution_date`, and `resolution_expiration`; backend code supplies no fallback dates. The creator name is prefilled from the authenticated account context but remains explicit in the tool call. The tool rejects missing/invalid dates, `acceptance_expiration >= resolution_date`, and a judging window shorter than 48 hours. A seven-day judging window is minting-agent prompt guidance, not a validation requirement. No fixed acceptance-window duration is imposed; the agent must choose an event-aware fair commitment deadline.

Do not add a separate structured judgment-source field. The immutable `resolution_contract` is the official terms and must state the intended evidence sources or source hierarchy in clear prose. The judging agent receives those terms prominently and judges against them rather than reconstructing a parallel source contract.

`acceptance_expiration` is always an exact timezone-qualified instant and is normalized to UTC for storage and serialization. On authoritative load or refresh, clients render it as a snapshot-relative label by flooring the largest complete remaining unit: days when at least one full day remains, otherwise hours, otherwise minutes, and `ACCEPT NOW` for a positive duration below one minute. Examples: 2.5 days becomes `ACCEPT IN 2 DAYS`; 1.2 hours becomes `ACCEPT IN 1 HOUR`; five minutes becomes `ACCEPT IN 5 MINUTES`; 53 seconds becomes `ACCEPT NOW`. Clients do not run a countdown timer solely to update this label. The server remains authoritative for expiration and atomic acceptance; the displayed label never grants eligibility after the stored instant.

`resolution_date` (`FIRST JUDGMENT`) and `resolution_expiration` (`RESOLVE BY`) render as exact device-local calendar date, clock time, and timezone rather than relative labels or date-only values. Include seconds when the stored instant is not aligned to a whole minute so a short-fuse Contract boundary is never rounded away. These labels do not count down; the stored UTC instants remain authoritative.

## Authentication and account

### `POST /auth/login`

Auth: public.

```json
{ "firebase_id_token": "firebase-client-id-token" }
```

The mobile client signs in or registers directly with Firebase Authentication using email/password, then sends a freshly obtained Firebase ID token here. The backend verifies signature, issuer, audience, expiry, Firebase UID, and claimed email with the Firebase Admin SDK before finding or creating the ThinkSo user. Invalid, expired, disabled, or revoked credentials receive `401 invalid_firebase_credential`. ThinkSo never receives the plaintext password. MVP deliberately does not require `email_verified == true`; see the known limitation.

```json
{
  "access_token": "opaque-database-backed-token",
  "refresh_token": "rotating-opaque-token",
  "expires_in": 86400,
  "user": { "id": "uuid", "display_name": null, "is_retired": false, "social_identity": null },
  "onboarding_complete": false
}
```

The mobile app stores both tokens in SecureStore and caches the access token in application memory while running. Access tokens expire after 24 hours. They are opaque and database-backed; every authenticated request also verifies that the associated session remains active, so logout, retirement, and administrative revocation take effect immediately.

Account creation, email/password sign-in, and password-reset email delivery are Firebase client operations, not ThinkSo API endpoints. A ThinkSo profile is created on the first successful Firebase ID-token exchange. Firebase's hosted action handler serves password-reset links for MVP. Email confirmation is deferred.

**OPEN security gate:** Firebase revokes its own refresh tokens after a password reset or major account change, but that does not inherently revoke an already-issued ThinkSo session. Before T-030 is complete, choose and test the mechanism that invalidates ThinkSo session families after such a Firebase revocation. Do not claim password-reset session invalidation until that mechanism exists.

### `POST /auth/refresh`

Auth: refresh credential.

```json
{ "refresh_token": "rotating-opaque-token" }
```

On success, rotate the refresh credential and return:

```json
{
  "access_token": "new-opaque-database-backed-token",
  "refresh_token": "new-rotating-opaque-token",
  "expires_in": 86400
}
```

Refresh credentials rotate on every successful exchange. A refresh-token family expires after 30 days without a successful exchange and after an absolute maximum of 180 days. The immediately previous credential has a 30-second reuse grace window for response-loss recovery; retrying it during that window returns the already-created successor credentials and never creates another successor. Use outside that window revokes the token family and returns `401 invalid_refresh_token`. An absent, expired, revoked, or retired-profile credential also returns `401 invalid_refresh_token`.

### `POST /auth/logout`

Auth required. Revokes the current device session and its refresh credential. The presented credential identifies the session; no separate device selector is required. Success: `204 No Content`.

The client treats this endpoint as best-effort. It clears local credentials and exits authenticated UI regardless of network availability or endpoint failure. Failure to reach this endpoint must never block or reverse device logout. Other device sessions remain active.

### `GET /me`

Auth required.

```json
{
  "user": { "id": "uuid", "display_name": "Mitchell", "is_retired": false, "social_identity": null },
  "onboarding_complete": false,
  "threads_connection_status": "NEVER_CONNECTED",
  "threads_last_verified_at": null
}
```

This response is used during splash/bootstrap and is served from ThinkSo state without waiting on a live Meta request. `threads_connection_status` is `NEVER_CONNECTED | CONNECTED | REAUTH_REQUIRED`.

### `GET /users/{user_id}`

Auth and active Threads connection required. Returns the minimal `UserRef` shown above. This is a platform-membership gate, not an ownership check: any active Threads-connected ThinkSo user may read it. MVP adds no profile counts or expanded public profile fields.

## Social integration

### `GET /integrations/threads/connect`

Auth required. Returns the authorization URL and CSRF state (**DERIVED**):

```json
{ "authorization_url": "https://...", "state": "opaque" }
```

### `GET /integrations/threads/callback?code=...&state=...`

Browser/OAuth callback. The route path is fixed as `/integrations/threads/callback`; `THREADS_OAUTH_REDIRECT_URI` supplies its exact environment-specific public HTTPS URL. Local development uses the owner's persistent ngrok development domain forwarding to the API on `localhost:8000`, so Meta can reach this otherwise-local route without a deployed API or an owned domain.

The callback verifies the single-use state, exchanges the code server-side, converts the result to a long-lived token, verifies the Threads identity plus `threads_basic` and `threads_content_publish`, encrypts the token, records its expiry, and only then marks the connection `CONNECTED` and onboarding complete. It then returns the browser to `thinkso://auth/threads/complete` with only a non-secret outcome code. The mobile client re-reads authoritative backend state before routing; no OAuth code, provider token, app secret, or identity data is placed in the application deep link.

If either required scope is absent, authorization is unsuccessful: do not mark the connection `CONNECTED`, do not admit the user to Main, and return them to Connect Threads with a retryable error explaining that publishing permission is required. A partial grant does not count as a Threads connection.

### Protected-action Threads gate

Every authenticated product endpoint other than session/account recovery requires `threads_connection_status=CONNECTED`. A stale or definitively invalid Threads authorization returns:

```json
{
  "error": {
    "code": "threads_reauthorization_required",
    "message": "Reconnect Threads to continue.",
    "details": {}
  }
}
```

Status: `403 Forbidden`. The backend persists `REAUTH_REQUIRED` before returning it. Transient Meta/network failure uses a recoverable service error and never changes connection state to revoked.

### `DELETE /integrations/threads`

Auth required. No body. Permanently retires the profile, voids every unresolved contract involving it, revokes Threads authorization, removes push tokens, invalidates all sessions, and preserves public historical records. Success: `204 No Content`.

This endpoint is the single destructive retirement operation; do not add a duplicate “delete account” route.

## Push tokens

### `POST /me/push-tokens`

Auth required.

```json
{ "token": "ExponentPushToken[...]", "platform": "IOS" }
```

Platform: `IOS | ANDROID`. Upsert the globally unique token to the authenticated user. Success: `204 No Content` (**DERIVED**).

### `DELETE /me/push-tokens/{token}`

Auth required. Removes only that token if owned by the caller. Success: `204 No Content`.

Send transactional pushes to all active device tokens of each intended recipient. Acceptance notifies the Contract creator with exactly `Your challenge was accepted!`. A supported verdict entering POSTING sends one result notification to both participants immediately, even though the Threads receipt may still be pending; the later POSTING-to-RESOLVED transition sends no duplicate. That result notification says exactly `Your judgment is in!` and does not expose TRUE/FALSE on the lock screen. UNRESOLVED notifies both participants with exactly `We couldn't resolve your challenge.` Every notification deep-links to the canonical Contract. Delete tokens reported permanently invalid by Expo.

The client asks for push permission only after its first successful Contract send or acceptance on that device, whichever happens first, and only after a ThinkSo primer. Registration occurs after operating-system authorization succeeds; the triggering send or acceptance never depends on permission being granted.

## Contract listing and reads

### `GET /users/{user_id}/record`

Auth and active Threads connection required. Returns the complete MVP Record for one user in a single response. This is a platform-membership gate rather than an owner-only ACL. OPEN/CLOSED membership and ordering are owned by the server. Each entry contains an explicit zero-based `record_order` and the full canonical contract.

```json
{
  "user_id": "uuid",
  "open": [
    {
      "record_order": 0,
      "contract": { "id": "uuid", "state": "SENT", "...": "full canonical Contract" }
    }
  ],
  "closed": [],
  "generated_at": "2026-09-01T18:00:00Z"
}
```

`record_order` is the server-authoritative absolute position within its OPEN or CLOSED collection for that response. Clients display entries by this field rather than treating array position as the ordering contract. A refresh atomically replaces both retained collections and their positions.

CLOSED order uses `terminal_at` descending. OPEN order uses these buckets in priority order:

1. `SENT` / awaiting acceptance, with newest `sent_at` first;
2. `JUDGING` or `POSTING`, with earliest `resolution_date` first;
3. `ACCEPTED` / active and upcoming, with earliest `resolution_date` first.

Within every bucket, the server uses a stable unique tie-breaker before assigning `record_order`.

MVP does not paginate this response. Pagination is explicitly deferred until dataset size or observed performance requires it; its future contract must preserve the one logical Record model and explicit ordering metadata rather than being inferred from array placement.

### `GET /contracts/{contract_id}`

Auth and active Threads connection required. Returns a canonical `Contract`. Any active Threads-connected ThinkSo user may view it; participant identity controls available actions, not read access. A cold invite/deep link is preserved locally while Login and Connect Threads are completed; the client must not request or render Contract data before both gates pass.

## Creation chat

### `POST /chats`

Auth and active Threads connection required. Creates a new creation chat. The client-generated ID makes initial creation retry-safe (**DERIVED exact request/response**).

```json
{ "id": "client-generated-uuid" }
```

The transaction creates the ACTIVE chat and persists the canonical assistant greeting exactly once. Repeating the same ID for the same owner returns the existing chat rather than creating another greeting. Success:

```json
{ "id": "client-generated-uuid", "state": "ACTIVE" }
```

### `GET /chats/{chat_id}/messages`

Auth and active Threads connection required; owner only. Response `Content-Type: text/event-stream`. First event is always authoritative full state:

```text
event: chat_state
data: {"chat_id":"uuid","state":"ACTIVE","messages":[{"id":"uuid","role":"ASSISTANT","text":"Okay, let's hear it. What are you so sure about?","status":"COMPLETE","created_at":"...","turn_id":null}],"proposals":[],"active_turn":null,"submission_gate":{"state":"OPEN","reset_at":null}}
```

Then zero or more:

- `message_created`: persisted user or completed assistant message;
- `text_delta`: transient assistant text delta;
- `tool_started` / `tool_finished`: safe UI activity labels, never hidden reasoning;
- `proposal_created`: `{ "turn_id": "...", "contract": <canonical Contract> }` after DB commit;
- `turn_completed`;
- `turn_failed`: safe display error;
- `budget_exhausted`: `{ "message": "You've used today's challenge budget. Try again tomorrow.", "reset_at": "..." }`.

When `turn_failed` follows an already-persisted user message, the client's retry action retries only that failed agent turn. The message is not POSTed again and must not be duplicated.

All live events carry `turn_id`; message events carry `message_id`. Send keepalives. Unknown event types must be ignored without closing/crashing the client. Reconnect emits a fresh `chat_state`; it is authoritative.

Message schema (**DERIVED**):

```json
{ "id": "uuid", "role": "USER", "text": "...", "status": "COMPLETE", "created_at": "...", "turn_id": "uuid" }
```

`role`: `USER | ASSISTANT`. `status`: `COMPLETE | STOPPED | INCOMPLETE`; `STOPPED` applies only to retained partial assistant output from explicit user cancellation, while `INCOMPLETE` covers partial output from a budget-ended turn. `turn_id` is nullable for the initial greeting. `active_turn` is null or `{ "id": "uuid", "status": "ACCEPTED | RUNNING | CANCELLING" }`. A completed turn may also have terminal status `BUDGET_EXHAUSTED`. `submission_gate` is `{ "state": "OPEN | DAILY_BUDGET_EXHAUSTED", "reset_at": "timestamp | null" }`. A budget notice is client presentation derived from this authoritative metadata; it is not an assistant message and never enters model context.

### `POST /chats/{chat_id}/messages`

Auth and active Threads connection required; owner only.

```json
{ "id": "client-generated-uuid", "message": "Bears are winning 10 games this year." }
```

Persist the user message and start one agent turn. Success: `202 Accepted` with:

```json
{ "message_id": "client-generated-uuid", "turn_id": "uuid" }
```

UUID uniqueness is enforced within the chat. Duplicate UUID returns `409 duplicate_message`; the client treats this as recovery and rehydrates through the GET stream. Different UUID with identical text is a valid new message. If a turn is already active, return `409 active_turn_exists`. A turn continues to completion and persists output even with no listeners.

Before persisting the message, gate non-exempt users against the locked USD $0.25 UTC-calendar-day minting budget. If exhausted, emit `budget_exhausted` to connected listeners and return `429 daily_minting_budget_exhausted` with `details.reset_at` set to the next UTC reset. Do not persist the submitted message or create a turn. This gate does not prohibit sending an existing proposal or completing system-owned judging, publication, notification, or retry work.

For an accepted turn, initialize the agent run with the user's remaining daily budget. Record actual GLM and OpenRouter server-tool charges after every completed provider response and do not dispatch another model step after exhaustion. An already-dispatched request may finish and create a bounded overage; its search `max_uses`, total results, and model output are capped in the provider request. End the turn `BUDGET_EXHAUSTED`, persist visible partial output as `INCOMPLETE`, emit `budget_exhausted`, and expose `DAILY_BUDGET_EXHAUSTED` in subsequent authoritative chat state. After reset, the existing retry command may rerun this turn from its original persisted user message without duplicating that message.

### `POST /chats/{chat_id}/turns/{turn_id}/cancel`

Auth and active Threads connection required; owner only. No body. Requests cancellation of an ACCEPTED or RUNNING turn and returns its current status. Repeating cancellation for the same turn is safe. Visible partial assistant text is persisted as a STOPPED message after cancellation; late provider output cannot become user-visible.

### `POST /chats/{chat_id}/turns/{turn_id}/retry`

Auth and active Threads connection required; owner only. No body. A FAILED turn, or a BUDGET_EXHAUSTED turn after its reset time, may be retried only while its chat is ACTIVE and no turn is active. The new attempt reuses the already-persisted triggering user message and returns `202 Accepted` with that message ID plus the new turn ID. It never creates another user message.

### `POST /chats/{chat_id}/abandon`

Auth and active Threads connection required; owner only. No body. Atomically changes an ACTIVE chat to ABANDONED and cancels any active turn. Repeating the command for an already ABANDONED chat is safe. The chat and late output become permanently unavailable to the user while remaining private operational history.

## Contract mutations

### `POST /contracts/{contract_id}/send`

Auth and active Threads connection required; creator only. No body. Atomically transitions the selected `PROPOSED → SENT`, stamps `sent_at`, marks its minting chat SENT with this Contract as the selected result, and cancels any active turn. It returns the canonical `Contract`; late turn output cannot become user-visible.

Retrying the same selected Contract after an ambiguous response is idempotent: if that chat already records this Contract as its sent result, return its current canonical Contract rather than sending again. If the chat sent a different proposal or the requested Contract was otherwise not sendable, return `409 contract_state_conflict`.

### `POST /contracts/{contract_id}/accept`

Auth required; active, Threads-connected profile that is not the Contract creator. No body. Atomically verifies non-expiration, `SENT`, and `caller.id != creator.id`, binds caller as challenger, transitions `SENT → ACCEPTED`, stamps `accepted_at`, and returns canonical `Contract`. Creator self-acceptance is forbidden for MVP even if a client bypasses the hidden UI control.

Already accepted—including by the same caller—fails with `409`; acceptance is not idempotent. Creator self-acceptance remains forbidden for MVP.

## Informational and internal operations

### `GET /how-it-works`

Do not create this API for MVP. How It Works, Terms, and Privacy are visible but nonfunctional placeholder controls; they expose no product data and open no destination. Real content and routing can be designed later.

### Judge command (not a public HTTP endpoint)

Run as an idempotent Railway scheduled command. It queries due ACCEPTED contracts, claims one safely, transitions it to JUDGING, and records attempts privately. A supported verdict is persisted with durable publication intent and transitions the Contract to POSTING. Failure to reach a supported verdict by `resolution_expiration` transitions to UNRESOLVED. Schedule at most eight substantive evidence attempts across the window, including First Judgment and Resolve By; infrastructure recovery retains the same attempt slot.

The judge must follow the immutable `resolution_contract`, including its stated evidence-source hierarchy. If no source permitted by those terms is available, attempts remain nonterminal until the window expires; the judge cannot substitute an unmentioned source merely to force a verdict.

The resolution terms also define evidence sufficiency. A single authoritative score or official numerical result may be enough, while a reporting- or consensus-based claim may require agreement among a stated number or class of qualifying sources. The judge must meet the contract's rule; there is no universal minimum citation count.

Once a supported TRUE or FALSE verdict is persisted, it is final for MVP. No participant-facing appeal, rejudge, or override endpoint exists.

### Consequence publication worker (not a public HTTP endpoint)

Claims durable due publication jobs. Successful Threads publication stores the provider post identifier/link and transitions `POSTING → RESOLVED`. Temporary failures receive eight attempts over 24 active delivery hours with backoff. After an ambiguous provider timeout, reconcile the losing participant's recent Threads posts for the exact approved text before retrying: a recovered post stores its receipt; confirmed absence permits retry; inability to establish either prevents a blind repost. Permanent nonauthorization rejection or failure to complete safely by the end of the delivery window transitions `POSTING → VOIDED` and cancels delivery. Invalid/revoked authorization moves the job to `BLOCKED_AUTH`, sets the social connection to `REAUTH_REQUIRED`, and pauses the delivery window with no further attempts until successful Threads OAuth resumes it. A verdict is never recomputed during publication retry.
